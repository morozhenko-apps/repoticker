## Specific security observations that must not be exaggerated

**Confirmed implementation properties (not test pass):** all five native Relay Secret commands invoke `settings_only(window)` to reject any label other than `settings`. `relay_prompt_secret`, `relay_stage_secret` and `relay_commit_secret_draft` additionally check window visibility. `relay_stage_secret` accepts the plaintext candidate from the Settings WebView IPC by documented design; it validates the base64url length and holds the candidate in a volatile draft, then writes to OS Keyring only after explicit commit. Therefore, do not describe the entire secret as never crossing any IPC. It is the *GitHub OAuth bearer* that never becomes a JS argument of `github_api_get`.

**Different origin evidence:** `github_begin`, `github_cancel`, `github_disconnect`, `save_settings`, `github_set_monitor_org` and `github_monitor_publish` take an `AppHandle` without an explicit `WebviewWindow` argument or a locally visible label check. This proves only that **those functions' own bodies do not enforce a window label**. The effective Tauri custom command permission, expected caller compatibility and host isolation have **not** been verified. The capability files describe core/plugin event and window permissions and do not, alone, prove per-command security. Do not change any authorization semantics without STOP FACTOR choices and native contract evidence.

**NM1 remains blocked:** `github_monitor_publish` checks `counts` and `coverage` as objects and the whole nested value's encoded byte length. This is *not* a strict nested field allowlist; a malicious nested token-like property can satisfy current top-level checks. Whether to reject/strip/preserve extra nested fields is an authorization/public contract decision. This is a **source-derived risk hypothesis**, not a reproduced user data leak. Continue other audit tasks without deciding this contract.

**Relay draft race remains a hypothesis:** `relay_commit_secret_draft` takes the draft from shared state before blocking OS vault write and only rechecks the result after the blocking task; `close_settings` can discard a draft, but the body does not show cancellation of a launched Keyring operation. A failed Keyring write returns the candidate to memory. Real interleavings RS1/RS2 must be reproduced through a controlled native seam to determine expected post-close semantics, before any fix to credential custody.

**GitHub OAuth cancellation/terminal phase:** `github_begin` checks the atomic attempt after obtaining a challenge, and `poll_authorization` checks active generation before and after HTTP poll and under `vault_gate` before credential write. There are terminal publishing sites whose prepublication `state.active(attempt)` check must be characterized under newer attempts, but code inspection alone cannot prove a stale event is published. Do not change the event contract based on AS1/AS2 without deterministic test barriers.
